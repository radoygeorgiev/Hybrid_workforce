1. Product goal and design rules

Help a site choose and deploy a better combination of people and technology. Start with the actual work. Match useful action bundles to supported products. Compare the complete process, its cost, and its evidence. Use measured site results to improve the next decision.

This is a proposed design for validation. The current owner request takes priority over older prototype limits. Deployment belongs in the target platform, even where the mockup uses planning screens and external integration placeholders. The AWS proof of concept remains a bounded learning project.

  • Match work, not job titles. A person can retain some actions while a robot performs others.
  • Count time, demand, dependencies, handoffs, and recovery. Action count alone cannot show staffing or cash savings.
  • Treat a product as a configuration: robot, tool, sensors, software, and interfaces.
  • Keep hard constraints separate from preferences. A known failure stays blocked. A missing value stays unknown.
  • Include the current method and manual process improvement. A valid recommendation can be stop or collect more data.
  • Use one case from opportunity through operation. The simulation is a service used by that case.
  • Use short sentences and stable terms. Explain units and missing data at the point of use.

Design terms: A task is a meaningful block of work. An action is a small observable step, such as scan or lift. A skill is behaviour under stated conditions. A capability is a measurable property that enables the behaviour. A work bundle is a set of actions that an actor can perform as a usable part of the process.

2. Proposed application flow

Demand and supply join at action matching. A process option can use more than one technology and more than one person. Performance work can run in parallel to a draft evaluation. It must not silently convert an unknown result into a pass.

The dashed feedback paths change the next case version. They do not overwrite the assumptions or evidence used for an earlier decision.

5. Matching, process design, and fleet logic

  • Build a baseline action graph. Record sequence, alternatives, repeat counts, and resources used at the same time.
  • Map action needs to skills and measurable capability limits. Test load, grip, reach, path, sensing, quality, tool, interface, and operating conditions as relevant.
  • Check each complete configuration. Return supported, blocked, unknown, or not assessed, with the reason and evidence. Supported by a claim is not proven at this site.
  • Form usable action bundles. A lift/carry/place sequence can require one actor to retain load control. Splitting it can add tooling, handoffs, or an invalid method.
  • Design current, improved manual, assisted, hybrid, and automated options where applicable. Show who performs every action and each recovery duty.
  • Search a bounded set of compatible configurations, robot counts, human roles, and shift plans. State search limits and exclusions. Do not claim a global optimum from a small sample.
  • Evaluate completed good units against the same demand and quality targets. Include charge and downtime definitions, shared chargers, queues, handoffs, buffers, and support work to the extent the selected model supports them.
  • If a simple model cannot represent an important shared resource or queue, show the limit and request a process evaluation. Do not make the local calculator appear to be a discrete-event or physics simulation.

For sequential actions, active work hours can start from demand × action frequency × active seconds / 3,600, summed by actor. Parallel actions and shared duties need explicit resource logic. Elapsed process time is not always the sum of all action times.

A simple fleet bound is required robot busy hours divided by usable robot hours, rounded up. This is only an initial capacity check. It cannot prove peak service, charger capacity, traffic performance, resilience, or the final staffing plan.

Example: a humanoid may handle 5 of 12 actions. Those actions might represent a small or large share of human work time. A person may still need to be present for scanning, recovery, or another critical action. The result must show action count, work-time change, staffing change, and cash benefit as separate fields.

6. Business-case logic and outputs

The EUR75,000 annual human cost, EUR100,000 robot price, and 40% coverage in the request are examples. They do not determine the robot count or savings. The 5,000-tote rate also needs a clear denominator: person or team, and shift or day.

Separate two business questions: Does this automation change create value? What extra value does this platform create compared with the existing engineering and delivery method? The platform cannot claim all robot savings as its own added benefit.

7. Performance evidence and confidence

Keep the datasheet-versus-first-simulation question open. The workshop contains competing views [S4]. A datasheet can provide a value and its stated conditions. It does not by itself prove the duration, error rate, or recovery cost of a new site task. A simulation result also needs input validity and a check against reality. AWS must define a suitable evidence plan for this PoC.

A statement such as 55% confidence is incomplete. It could mean a 55% chance of one successful grasp, meeting shift output, or making a positive business case. These are different events. Do not merge them into one score. A measured success-rate estimate can have statistical uncertainty, but its validity still depends on the sample and operating conditions.

For version 2, use clear source labels, explicit gaps, conditional results, and scenario ranges. Add a quantitative probability only when there is a defensible method. A financial improvement must never increase the displayed quality of technical evidence.

8. Deployment, pilot, and improvement

Deployment starts from the selected scenario. It is a shared module across technology types. It includes site preparation, interfaces, an execution route, release records, tests, pilot planning, observations, and support. It may include model or policy training where the selected hardware and task require it.

AWS and the OEM must explain the actual humanoid stack. The platform must not assume that it will create a robot brain from scratch. Some solutions use OEM configuration and commissioning. Others need model adaptation, control work, simulation, demonstration data, or training. The deployment plan must name each dependency and its owner.

The platform coordinates planning, records, service requests, and decisions. Real-time machine control, safe motion, and the vendor fleet controller remain separate technical boundaries unless a later design explicitly assigns that role.

The improvement loop is controlled: collect trial data, check its quality, compare with the baseline, revise the affected records, test the change, and review a new release. Do not automatically retrain or load hardware after each new observation.
